## 原题逐项要求

原题第2～3页规定：先读取一行N，每次输出一个0-based下标并立即刷新，再读取一行非负整数清晰度；最后输出独立一行DONE并以0退出。最后真实查询决定停车位置。

| 检查 | 原题要求 | 求解器控制 |
| --- | --- | --- |
| 下标 | 0≤idx<N | 统一传输层再次检查 |
| 查询输出 | 一行整数，ASCII | to_chars编码整数；只由传输层写stdout |
| 行长 | 内容≤64字节；LF或CRLF | 下标至多3字节；DONE为4字节 |
| 刷新 | 每次输出及时刷新 | 每次fwrite后fflush |
| 结束 | 必须输出DONE | 正常收尾、可捕获异常收尾及幂等析构保护 |
| DONE后输出 | 禁止再写协议输出 | doneSent阻断后续查询和重复DONE；调试仅stderr |
| 消息 | 不超过201条输出消息 | 查询≤199，因此查询加DONE≤200条 |
| 退出 | 退出码0 | 捕获求解器构造/运行的C++异常并收尾 |
| 超时/内存 | 每例10秒，512MB | 保留既有时间预留；本地未强制执行512MB限制 |

Q≥200、振荡≥7、冗余≥200属于合法零分条件。协议错误、超时、资源错误会让整份作品失败，不能混为一谈。internal_error及-1不是有效算法总分，也不能单凭该枚举证明服务故障或求解器故障。

## 实际C++修改

[加固后的候选源码](../../data/experiments/protocol_audit_20261027/main_protocol.cpp)增加统一Protocol传输层，记录已发出的查询和消息；不再仅依靠收到回复后的算法计数。传输层拦截越界、超额、DONE后查询，使用整数编码和C标准输出刷新。DONE具备幂等保护。捕获构造/运行的C++异常后尽量合法收尾；尚未查询时先发一次合法查询。

异常收尾不保证该例高分，也无法处理操作系统强制终止、段错误或不可捕获的资源故障。它修复了异常路径缺少协议收尾的实际弱点，但尚不能证明这就是此前线上失败的根因。正常算法分支及参数没有改变。正式203239源、失败A快照和其已有证据均不改写。

- 1640条去重数组，其中1176条新鲜母曲线，原版/加固版共3280次真实管道交互。
- 两版协议错误均为0，查询轨迹及分数全部相同；线上internal_error没有在本批正常输入中复现。
- 加固版最大查询199、消息200、振荡5；本机最大单例耗时0.265秒，不据此推断官方机器性能。
- [4项实际C++回归测试](../../dev/tests/test_protocol_transport.py)检查越界拒绝、199次输出上限、重复DONE、DONE后查询、整数极值、输入中断和构造异常。
- 构造异常由单独测试桩注入，不是声称发现了真实隐藏样例。强制一次vector分配抛出bad_alloc后，加固版发出一次合法查询、DONE并以0退出。
- 初次新增测试错误地仅接受LF；已按原题同时接受LF/CRLF，未放宽任何原有策略断言。
